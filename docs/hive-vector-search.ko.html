01 / 역할 분담

FTS를 버리지 않은 이유

정확한 번호와 표현이 다른 질문은 서로 다른 문제. 하나의 검색 방식으로 모든 질문을 해결하기보다, 필요한 경로를 선택하는 구성.

SOURCE OF TRUTH

Markdown

사람과 에이전트가 읽고 수정하는 지식 원문. 내용·출처·연결의 유일한 정본.

벡터 생성 때문에 원문 이동·변환·삭제 없음

EXACT & TEXT SEARCH

SQLite FTS

식별자·오류 문구·날짜·숫자처럼 정확한 표현을 찾는 기본 검색.

예: DOC-142, 자료 00500

SEMANTIC CANDIDATES

sqlite-vec

문서와 질문을 숫자 벡터로 비교해, 말은 달라도 뜻이 가까운 후보 탐색.

예: “지운 자료 찾기” ↔ “백업 복원 절차”

예시는 용도 설명용. 실제 연결·의존·영향 관계는 별도의 Markdown 관계 그래프와 Graphify 코드 그래프 담당. 벡터의 가까움은 인과관계나 사실의 참·거짓이 아님.

02 / 지식 → 벡터

처음 한 번의 큰 계산,
이후에는 달라진 부분 중심

01원문·권한 확인허용된 모음의 Markdown과 현재 등록부·공개 범위 검증
02변경 지문 비교내용과 처리 계약이 같으면 기존 계산 재사용

실제 구현

긴 문서도 끝까지

모델 입력은 128토큰 구간으로 분할. 각 구간에 제목 문맥을 붙이고 전체 본문 구간의 결과를 가중 평균·길이 정규화.

문서 끝부분을 잘라 버리는 방식과 구분

실제 검증

49,900개 재사용

5만 청크 중 100개 변경 시험에서 새 계산 100개, 나머지 49,900개 벡터 바이트 보존 확인.

작은 변경에 유리한 구조. 100개 비용을 1개 비용으로 단순 나누는 추정은 제외.

생성 속도와 재개를 위해 적용한 구현
  • 같은 실행 환경을 승인한 공유 모음만 최대 100개 지정, 16개씩 처리
  • 한 모델을 공유하며 최대 4개 DB 동시 처리, 전체 변환 작업 수는 요청 예산 이하
  • 입력·게시 전후 정본 검사는 최대 4개 병렬화, 모든 검사 성공 뒤에만 결과 반영
  • 시간 제한 시 검증된 중간 결과만 재개, 실패한 작업 파일의 활성화 금지
  • Windows 혼합 CPU의 같은 성능 등급 사용으로 반복 계산의 수치 차이 방지. 기존 사용자 CPU 제한 보존
  • 열린 파일의 검증된 크기를 읽기 버퍼 힌트로 사용하되, EOF·크기 상한 검사는 유지

03 / 질문 → 근거

두 검색 경로, 하나의 검증된 결과

기존 knowledge-recall의 검색 선택과 연결. 기본값은 FTS, 명시적 --mode semantic은 벡터와 FTS의 결합. 새로운 검색 Skill ID 추가 없음.

표현이 다른 질문 → 의미 검색 선택
로컬 모델로 질문을 변환하고 두 경로의 후보를 결합. 실제 검색을 실행하지 않는 흐름 설명.
SQLITE FTS

단어·표현 경로

  1. 현재 범위의 FTS 조회
  2. 정확한 별칭·번호·문구 확인
  3. 기존 텍스트 후보와 순위 유지
MINILM → SQLITE-VEC

의미 경로

  1. 동의된 실행 환경·색인 확인
  2. 질문을 384차원 벡터로 변환
  3. 허용된 DB에서 가까운 후보 탐색
후보 결합 → 원문·권한 재확인 → 인용 반환

질문별 점수 정규화 · 벡터 0.75 + FTS 0.25
정확 일치 보호 시 FTS 순서 우선 · 최종 순서는 fusion_rank

“자료 00500”은 정확히

짧은 이름과 번호도 정확 일치 보호 대상. 의미 점수가 높은 다른 문서 때문에 정확한 FTS 결과가 밀리지 않도록 보강.

00500과 005000, 부호·소수·비율 차이의 엄격한 경계 검사.

답변 생성은 호스트의 몫

Hive의 반환값은 관련 근거와 출처. 실제 설명·답변 작성은 활성 구독 호스트의 작업.

로컬 임베딩 모델은 문장을 생성하는 챗봇이 아니며, 모델 제공자 API 호출·API key 요청 없음.

벡터를 사용할 수 없을 때
미설치·손상·처리 계약 불일치·오래된 벡터는 검증된 FTS 경로로 복귀. search.used와 search.fallback에 실제 사용 경로 표시. 벡터를 요청했다는 이유만으로 사용 성공 처리 금지.

05 / Hive 연결과 경계

같은 검색 기능, 섞이지 않는 지식 범위

명시적으로 허용된 범위 안에서만 읽기·검색
Hive 소스개발 문서·소스 Wiki 전용 경로. 소비자 프로젝트와 분리.
프로젝트·공유등록·승인된 모음의 파생 DB. 검색 범위 밖 결과 제외.
비공개모음별 명시적 활성화와 물리 분리. 다른 프로젝트로 자동 확대 없음.
기밀생성과 조회의 현재 작업 승인 분리. 조회 승인의 일회성 소비.

Hive 개발 소스

개발용 파생 자료. docs/facts/의 원문과 분리, 소비자 패키지에 포함하지 않는 경계.

설치 승인과 데이터 보존은 별개로 엄격하게

  • 미리보기의 정확한 모델·패키지·용량·경로에 동의한 뒤에만 설치
  • 미완료 세대의 게시 금지, 실패 시 이전 정상 세대와 FTS 유지
  • .hivekb에는 벡터·모델·캐시 제외, 다른 환경에서는 정본으로 재생성
  • 백그라운드 서버·감시·자동 MCP 등록·제공자 API·질의 기록 없음

고정 신뢰 코드의 검사와 실제 시험으로 확인한 경계. 운영체제 차원의 완전한 네트워크 샌드박스 또는 모든 공격의 차단 증명과 구분.

07 / 실제 사용

사용 전에 알릴 세 가지

FIRST BUILD

첫 생성은 길게

모델 다운로드와 지식 전체의 첫 계산에 시간·디스크·메모리 필요. 자료 양과 PC에 따른 차이 안내.

이번 5만 자료에서는 생성 약 11분, 모델 작업 트리의 표본 최대 RSS 약 4.70GB. 모든 사용자의 고정 요구량은 아님.

SMALL CHANGES

변경한 부분 중심

내용·처리 계약이 같은 지식은 재사용. 작은 추가·수정은 대량 재계산보다 유리한 구조.

프로세스 준비·파일 검증의 고정 비용도 존재. 현재 실측으로 1–10개 갱신 시간을 단정하지 않는 안내.

A FEW SECONDS

의미 검색은 수 초

질문 변환·벡터 탐색·FTS 결합·인용 검증을 포함한 대기. 정확한 코드·문구 조회에는 기본 FTS 사용.

원문·색인이 없거나 오래되면 자동 무제한 생성 대신 현재 상태와 필요한 조치 안내.

“작업 동안 모델 유지” 제안의 결론

조회 때마다 모델을 다시 준비하는 비용을 줄이려던 벡터 성능 개선안. 검색 기능이나 보안 결함을 해결하기 위한 필수 단계가 아님.

이번 범위에서는 생략. 현재 성능 수용에 따라 새로운 연속 실행 방식·상주 모델·백그라운드 서비스 추가 없음. 현재 단발 실행과 요청별 검증 유지.

명령 예시와 운영 주의사항
다음은 사용자·프로젝트 지식용 명령 형태. 다운로드·설치 전에 미리보기 확인과 별도 동의 필수. Hive 소스에서는 source-wiki vector 경로 사용.
hive knowledge vector preview --user-root <user-root> --target <project-root> --collection user-root --visibility shared --python <python> --output json

hive knowledge retrieve --user-root <user-root> --target <project-root> --scope auto --query "지운 자료를 되찾는 방법" --mode semantic --output json

전체 명령·동의·재개·rollback: 선택형 의미 검색 사용 안내. fresh의 미시작 모음은 새 계산 유지, 이번 실행의 검증된 중간 결과만 resume 사용.
