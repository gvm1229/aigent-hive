## 먼저 읽을 결론

**사용자에게 전달 가능한 검증 완료 0.14.0을 만들지 못한 상태.** 장기간 작업에도 첫 공개 시험판 미게시, 원래 완료 조건 대부분 미종결, 최소 신규 프로젝트 입력의 실제 결함 잔존.

재사용 가능한 제품 구현과 부분 검증은 존재. 그러나 기반 코드·복구 세부·회귀·문서 보정의 누적을 사용자 흐름의 완결로 연결하지 못한 수행 실패. 커밋 수·코드 분량·시험 횟수로 이 결과 부재를 대신 설명하는 방식의 중단 필요.

사용자의 **48시간 이상 정체** 보고를 이번 감사의 핵심 문제로 취급. Git 시각만으로 정확한 순수 작업 시간이나 유휴 시간을 산출할 근거는 부족. 정확한 시간 합계의 미확인과, 완료 제품 전달 실패의 확인은 별개.

다음 구현의 첫 대상은 새로운 기반 구조가 아니라 **이미 문서화한 네 항목의 신규 프로젝트 답안 → 적용 → 검증 → 재개** 흐름. 이 입력의 현재 실패를 먼저 고친 뒤 같은 입력으로 실제 Luna 평가 재실행. 구현을 통째로 교체하거나 완료 기준을 줄이는 해결책 제외.

### 1.3 유지할 설계

- 질문·조건·기본값·검증·저장의 소유자는 Rust CLI. 터미널·답안 파일·AI 입력은 같은 적용 엔진의 입력 경로
- 제공자 API 호출·API 자격 증명 요청·호스트 모델/속도 설정의 자동 변경 없음
- 설정값과 선택 출처를 같은 정본 파일에 저장. SQLite는 재생성 가능한 파생 색인
- 답변 임시 저장 → 전체 미리보기 → 확인 → 적용 → 검증. 매 질문마다 실제 설치 상태를 변경하는 방식 제외
- 기존 설치 소유자, 잠금, 파일 비교 후 교체, 복구 기록, 버전 호환 코드를 재사용
- 전역 갱신으로 등록 프로젝트 전체를 몰래 수정하지 않는 경계. 프로젝트 변경은 명시한 대상에서 수행
- 보호 비활성 판정과 작업 실행 승인은 별개. 보호가 꺼져 있어도 실행 권한·대상·소유자·동일 요청 검증은 유지

### 2.3 설정·진행 자료의 유지 조건

- 사용자 정본: `.hive/config/user-setup.yml`, 프로젝트 정본: `.hive/setup-answers.yml`. 새 적용의 schema_version2와 기존 v1 읽기 호환
- `preference_decisions`의 키: JSON Pointer. 값: `origin`, `input_channel`, `scope`, `question_id`, `question_revision`, `policy_version`, `changed_in_version`, `decided_at`, `value_digest`, 필요 시 `inherited_from`
- 입력 경로: `terminal`, `answers-file`, `agent`, `migration`. 출처 불명에는 실제 답변 시각 생성 금지
- 값과 출처의 같은 파일 교체. 직접 편집은 값 보존과 `external-change` 판정, 동시 변경은 충돌 반환
- 진행 파일: 사용자 루트의 `.hive/config/setup-progress/user.yml` 또는 `projects/<target-digest>.yml`. 다른 프로젝트·복제/이동된 폴더에 자동 재사용 금지
- 구현 진행 단계: `awaiting-answers`, `previewed`, `applying`, `recoverable-failure`, `complete`. 계획의 논리 단계와 실제 저장 enum의 구분 필요
- 완료/취소/제거 이력: `.hive/history/lifecycle/<operation-id>.json`, 범위별 최근100개. 미완료 복구 자료의 자동 삭제 금지
- 출처·기록은 실행 승인이나 감시 동의의 대체 자료 아님. 사용자 원문·비밀·모델 추론·실제 호스트 세션 결합 저장 금지

| 경계 | 원래 제한 |
| --- | --- |

- 실제420/90초의 과거 통과와 최신 공개 파일의 전체 시간 경계 수용을 구분. 이미 확인한 과거 실행을 매 보조 수정마다 반복하는 방식 제외

### 3.2 M02-C2와 중복 정리의 현재 사실

원래 지적된 “복구 독자는 연결됐지만 인계 생성은 시험에만 존재” 문제는 현재 소스에서 수정된 상태.

- 실제 생성 호출: `crates/hive-cli/src/user_setup/setup_engine/monitor_review.rs`의 `next_store.handoff_monitor(progress, answers, &stopped)`
- 인계 저장/복구: `user_setup/progress_store/monitor_review.rs`
- 고정 경로: `.hive/config/setup-progress/monitor-handoff.json`
- 공통 적용 기록: `user_setup/setup_engine/application.rs::begin/finish`
- `begin`: Applying 진행 저장과 적용 시작 기록
- `finish`: 성공 완료 기록 또는 실패 기록. 각 입력 경로의 동의·잠금·기한·작업자·출력은 호출자에 유지
- 터미널/파일/복구/구형 적용의 공통 부분을 위 함수로 모으고 해당 중복 처리 제거
- 감시 정지 확인을 나타내는 `StoppedReader`와 같은 사용자 폴더 결합 유지
- 옛 작업은 취소, 새 작업은 다른 ID로 이어받고 `midway.enabled=false` 및 그 출처만 변경
- 후속 하네스 실패 때문에 옛 감시 동의를 자동 재활성화하지 않는 경계 유지

남은 것은 더 큰 인계 체계를 만드는 일이 아니라 **격리 Windows에서 실제 예약·감시·앱 제어까지 같은 흐름이 성립하는지 확인하는 수용**. [철회 복구](../plans/details/monitor-consent-withdrawal-0.14.0.md)와 [C2 상세](../plans/details/monitor-setup-review-0.14.0.md)의 기존 설계 보존.

## 4. 무엇이 잘못됐는가

### 4.1 장기 정체의 중심 원인 — 수행 방식의 실패

1. **완료 단위보다 수정 단위의 누적:** M02의 복구 하위 단계, 이전, 보호 지침, 갱신, 제거, 얇은 Skill, 전체 CI 보정으로 범위 확장. 개별 원래 완료 조건의 종료가 뒤로 밀린 흐름.
2. **기본 성공 경로의 늦은 확인:** 기존 설정 수정·오류 거부·복구 시험은 존재했지만, 새 프로젝트의 문서화된 최소 답안 성공은 놓친 상태. 실제 Luna 시험에서 뒤늦게 노출.
3. **형식 검증과 사용자 결과의 거리:** 함수/자료형/정적 문구·사본 검사가 통과해도 사용자 명령 전체의 성공을 뜻하지 않는 간극 관리 부족.
4. **수용과 CI 보정의 반복 전환:** 확인한 개별 회귀 뒤 다시 전체 검사에서 다른 계층의 실패 발견. 플랫폼 조건부 코드, 새 출처 파일의 줄바꿈, 정확한 버전 표시처럼 최종 입력에서만 드러난 결손.
5. **집계 정합성 부족:** M 단계의 “완료”와 원래15개 항목의 미완료가 병존. 어느 원래 조건이 아직 부족한지 매번 명확히 닫지 못한 보고 방식. 6.7%를 반복하면서 사용자가 체감할 완료 결과를 제공하지 못한 문제.
6. **검증 도구 자체의 품질 부족:** 실행되지 않은 검사 목록이 보고서에 남거나, 모델 실패에서 입력량을0으로 집계하는 문제. 도구 준비 오류와 제품 오류를 구분하는 추가 비용 발생.
7. **불필요한 탐색·재시도 비용:** 확인하지 않은 경로/옵션으로 실패한 명령, 너무 큰 읽기 결과의 잘림, 검사 도구 인수 누락, 범위를 넓힌 뒤 재검증하는 작업 존재. 필수 검증과 별개인 실행 비효율.

실제 Luna 호출에는 별도 승인이 필요했으나, 모델 없이 문서의 최소 답안을 직접 CLI로 확인하는 검사는 그 승인과 독립적으로 가능. 모델 승인 대기를 기본 성공 경로 누락의 충분한 설명으로 삼을 수 없는 상태.

환경 부재나 엄격한 안전 조건만으로 설명할 수 없는 실패. 이미 있는 구현을 끝까지 연결하고, 첫 성공/실패 경로를 빨리 실행하고, 남은 조건을 줄이는 책임은 이 에이전트에 존재.

### 4.2 확인된 최우선 제품 결함: 신규 작은 답안

문서가 요구하는 최초 네 항목을 모두 준 합법적 입력:

```json
{
  "schema_version": 1,
  "kind": "hive.setup-answer-patch",
  "answers": {
    "setup_mode": "expedited",
    "project_name": "luna-quick",
    "project_kind": "general",
    "primary_host": "codex"
  }
}
```

격리된 개발 CLI의 실제 결과:

```text
exit_code: 2
code: hive.setup-invalid-input
message: setup answers violate the contract: missing field `usage_stop_remaining_percent`
changed_paths: []
```

- 위치: `crates/hive-cli/src/user_setup/setup_engine/project/file_input.rs::normalize`
- 원인: 저장값 없는 작은 답안의 초기 내용을 `{"schema_version":2}`만으로 구성한 뒤, 필수 설정이 필요한 renderer 구문 분석 실행
- 이미 있는 올바른 기본값 함수: `project/questions.rs::defaults(target, global, host)`
- 현재 기본값 함수의 내용: 전역 하한, 두 심사 정족수, 빈 역할/선택 기능, 비밀 파일 제외 규칙, 빈 지식 승격 범위 등
- 최소 수정 방향: 신규 작은 답안의 초기값에 위 공통 기본값 전달. 네 명시 선택 요구는 유지하고 그 위에 제공한 값만 병합
- 보존 조건: 이 기본값을 “기존 저장된 사용자 선택”으로 위장하지 않는 구분. `previous=None`의 출처 의미와 `agent`의 시각/인간 동의 비주장 유지
- 금지 방향: Skill에 전체 YAML 작성을 다시 요구, 모델이 빠진 필드를 하나씩 추정, 초기 필수값 검사 삭제, 보안 제외 목록 제거, 새 설정 프레임워크 추가

필요한 합격 확인: 네 항목만으로 새 프로젝트 apply/validate 성공, 전역 하한 상속, 비밀 제외 규칙, 빈 역할/후크, 사용자 파일 보존, Agent 출처·시각, 같은 입력 재적용, 적용 중 종료 후 재개. 필수 네 항목 누락·잘못된 범위·동시 변경 거부는 유지.

### 5.3 완료를 강제하는 작업 규칙

- **동시에 한 사용자 흐름:** 구현·결과·취소·실패·재개를 포함한 단위. 보조 커밋은 기능 완료로 집계 제외
- **첫 정상 흐름 우선 실행:** 이번 최소 답안처럼 사용자가 가장 먼저 쓰는 입력을 기능 구현 직후 확인
- **결과 중심 판정:** 실제 저장값·권한·역할 본문·외부 바이트·실행 상태와 출력 대조. 함수 호출·파일 존재만의 성공 판정 제외
- **근거표의 한 줄 닫기:** 원래 조건, 구현 위치, 정확한 시험, 성공 신호, 남은 플랫폼/입력, 다음 행동을 한곳에 연결
- **변경된 실패만 재검사:** 이미 통과한 판단을 새 요구·상반 근거·회귀 없이 다시 열지 않는 원칙
- **전체 검사는 경계에서 한 번:** 관련 검사 뒤 묶음 변경의 정확한 소스로 CI 실행. 매 문서/보조 커밋마다 전체 제품 시험 반복 제외
- **기록된 시험 중 소스 수정/커밋 금지:** 실행 전후 소스 지문 확인. 전역 동시 작업도 같은 제약 고려
- **고정 실패의 반복 제한:** 명령·입력·환경 중 무엇이 바뀌었는지 설명할 수 없는 재시도 금지. 모델의 필수값 추정 보충도 금지
- **실제 수용 경계 유지:** 환경 변수 격리를 VM/컨테이너 격리로 표현하거나, 가짜 앱 성공을 실제 앱 성공으로 표현하는 처리 금지
- **진행 보고 개선:** 원래 완료율과 함께 이번에 닫은 사용자 행동, 정확히 남은 조건, 다음 하나의 흐름 제시. 커밋/시험/줄 수의 대체 점수 금지
- **소스 보존:** 유효한 과거 근거·실패·호환 코드·공통 정책 보존. 실제로 중복이며 동등성이 확인된 부분만 제거
