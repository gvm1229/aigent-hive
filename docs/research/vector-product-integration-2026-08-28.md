### 단일 검색 안의 SQLite 적재 재사용 계획

- 초기 검색 범위 확인과 최종 FTS·벡터 결합이 같은 RAG를 다시 해석하는 비용 축소
- 같은 `RagStore`·전체 요청에 결합한 비공개 일회성 검색 상태만 유지. 다른 요청·모음·사용자 루트 재사용과 복제 금지
- 모델 실행 중 정본 잠금 해제. 최종 단계에서 dirty·manifest/trust·전체 등록부·현재 SQLite 바이트를 새로 확인
- 전체 파일 SHA·manifest 전체·등록부 전체가 초기 값과 같을 때만 기존 읽기 전용 연결 재사용. 논리 지문 하나만의 대조 금지
- 최종 후보·요청 예산·반환 정본·scope 제어 기록 검사 유지. 실패 시 상태 폐기 후 기존 FTS를 새로 검증
- 기밀 승인 소비 순서 유지. 새 공개 명령·서버·다음 질문까지의 캐시 없음
- 검증: 중간 SQLite/manifest/trust/등록부 변조, 반환 원문 변경, 다른 요청 사용 불가, FTS 대체와 메모리 비용
- 요청 사이 모델 재사용은 별도 선택지이며 이 변경에 포함하지 않음

### 증분 처리의 반복 비용 축소 계획

- 목적: 100개 모음의 반복 모델 시작·전체 RAG 적재 감소. 30초 기준 유지, 기존 실패 기록 보존
- 기존 `knowledge vector rebuild`의 `--collections` JSON 배열로 정확한 목록 지정. 단일 `--collection`과 혼용 금지, 자동 전체 모음 선택 없음
- 같은 사용자 루트·동일한 승인 실행 환경·이미 활성화된 shared 모음 최대 100개만 허용. 별칭 중복·미승인·source·private·confidential 묶음 거부
- 한 실행은 최대 16개 모음씩 처리. 각 구간의 전체 입력은 기존 5만 청크·256MiB 한도 준수, 전체 실행 예산 만료 시 나머지는 미시작으로 반환
- 구간별 RAG 적재·검증 한 번과 모델 한 번만 공유. 모음별 DB·제어 기록·불변 세대·정본 지문·물리 경계 유지
- 정렬된 scope 잠금 → 정본 잠금 안 입력 검사 → 정본 잠금 해제 후 계산 → 새 RAG/정본/권한 검사 뒤 게시
- 게시 구간의 중간 변경은 게시한 제어 기록만 역순 비교 후 복구. 구간 간 전체 원자성 주장 없음, 완료·미완료·미시작 구분
- 새 저장 형식·상주 서버·자동 설치·권한 확대 없음. 단일 모음 경로와 공통 계산/게시 절차 재사용
- 구현 순서: 공유 입력/게시 API·회귀 → 제한된 보조 계산 → CLI 연결 → 실제 단일/묶음 동등성·잠금·증분 측정
- 필요한 반례: 중복/범위 거부, 다른 실행 환경, 도중 정본·권한·SQLite 변경, timeout/취소, 다른 모음 보존, 기존 단일 명령과 경합
- 전체 검색의 500ms/2초 기준은 별개. 증분 최적화로 검색 지연 해결 주장 금지

### 대규모 실제 자료에서 발견한 저장 한도 불일치

- 실제 Wiki 50,000개·shared collection 100개로 만든 RAG SQLite는 197,865,472 bytes
- RAG 허용 한도 256MiB와 공통 파일 게시기의 128MiB 한도가 달라 정상 자료의 게시 실패
- 자료나 검증을 줄이지 않고 게시기 한도를 RAG 계약과 일치시킴. 한도 초과 거부는 유지
- 실패한 임시 파일 검증에서도 생성한 임시 파일을 정리하고 기존 파일을 보존하도록 회귀 추가
- 실패 때 원본 문서·등록부는 보존됨. 이 실패는 벡터 모델 실행 전의 기존 저장 경로 결함
- 수정 바이너리 `5207bf9109e43f9918e3f01777dc5c4952fce612a4119447fb266f8e52a9d19a`: 실제 FTS 갱신 17.929초, 문서·청크 각 5만 개 정상 저장
- 첫 FTS 갱신에서 등록부의 JSON 표현이 YAML로 정규화됨. 101개 항목의 모든 논리 내용과 정본 문서는 동일, 등록부 바이트 동일 주장은 하지 않음
- 이후 벡터 설치·생성의 등록부 보존 기준은 이 정상 FTS 준비 직후 바이트로 고정
- `vector-scale-100/preparation.json`, `registry-normalization.json`, `cleanup-receipt.json`: 실패 임시본은 활성 색인과 전체 해시 일치 확인 뒤 정확한 파일 하나만 정리

### 추가 승인 후보: 비생성형 로컬 재정렬

- 의미 후보 검색 뒤 질문·문서 쌍을 함께 읽고 관련성 점수만 계산하는 별도 모델
- [Sentence Transformers의 공식 검색·재정렬 방식](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)은 빠른 후보 탐색과 정밀 순위 계산을 분리
- 공개 후보 [다국어 mMiniLMv2 재정렬 모델](https://huggingface.co/cross-encoder/mmarco-mMiniLMv2-L12-H384-v1): Apache-2.0, ONNX 제공. 한국어 정확도·현재 CPU 지연은 미검증
- 기존 로컬 실행 예외는 임베딩 색인 계산에 한정. 재정렬 모델 실행·의존성 추가 전 유지보수자 승인 필요
- 승인 시 원본·독립 질문을 변경하지 않고, 정확한 사실 검색 무회귀·전체 지연·모델 용량을 함께 측정
- 제공자 API·글 생성·기준 완화 없음. `0.10.0` 후보이며 이후 버전으로 자동 이월하지 않음

### 현재 승인 범위

- 추가 모델 없이 가능한 비교: 순위만 더하는 RRF와 검색 점수의 정규화 결합 비교
- [혼합 검색 결합 함수 연구](https://arxiv.org/abs/2210.11934)의 점수 결합을 참고하되, 다른 자료의 우위를 Hive의 통과 근거로 사용하지 않음
- 현재 실제 FTS 점수와 벡터 거리 점수에 질문별 최소·최대 정규화 적용, 벡터 비중 0.25·0.5·0.75만 사전 지정
- 원본 120문항으로 후보를 선택한 뒤 독립 문항으로 별도 확인. 문항·정답·기준 수정 없음
- 사전 지정 비중 0.25·0.5·0.75의 원본 의미 결과: 86.7%·91.7%·95.0%, 정확 질문은 모두 100%
- 벡터 비중 0.75만 후속 독립 평가 후보로 선택. 이 탐색 뒤 위의 실제 CLI 검증으로 연결, 새 모델 실행 없음

- 초기 생성 보강 후보: 같은 ONNX 모델을 한 프로세스에서 공유하는 제한된 스레드 묶음과 기존 다중 프로세스 비교
- [ONNX Runtime의 동시 실행 계약](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/session/inference_session.h)과 [스레드 설정 안내](https://onnxruntime.ai/docs/performance/tune-performance/threading.html)를 기준으로 CPU만 검사
- 모델·본문 길이·batch·질문·채택 기준 변경 없이 메모리·실제 시간·벡터 결과 동등성 검증 후 적용
- 공유 CPU 세션의 3,072개 탐색: 8개 스레드 33.99초·최대 작업 메모리 2.27GB, 12개 27.21초·2.88GB. 전체 생성 시간으로 환산해 통과 처리 금지
- 이전 다중 프로세스 결과와 일부 벡터의 최대 성분 차이 약 0.00014. 동일 입력 64개는 순차 3회·동시 24회 바이트 일치
- 서로 다른 512개 입력도 순서를 바꾼 동시 32회 실행에서 각 순차 결과와 바이트 일치
- 동시 실행의 같은 입력 반복과 실행 구성 변경의 수치 차이를 구분. 최종 검색 결과·전체 비용 검증 전 출하 방식 확정 금지

1. 고정된 최적화 빌드로 원본 120개·독립 60개 질문의 실제 CLI 재검증
2. 최종 후보의 고유 5만 청크 전체 생성·100개 변경·중단 재개·전체 재생성 동등성
3. 실제 CLI 전체 시간·범위별 디스크 사용량·승인/기밀 경계 재검증
4. Windows x64·macOS arm64·Linux musl의 고정 바이너리 수용
