# 프로젝트 전체 정책 검사와 훅 적용 분석

- 날짜: 2026-09-18
- 기준 소스: `35ed56ff`, 목표 제품 `0.11.0`
- 요청 범위: 브랜치 외 전체 규칙의 적용 가능성 분석과 처음부터 설계할 경우의 제안
- 실행 환경: Windows Codex, 코드·지침의 읽기 전용 조사
- 제품 구현·호스트 훅 설치·원격 설정 변경 제외

## 분석 순서

1. 소스 개발·제품 실행·설치·지식·출시의 규칙과 실제 검사 위치 대조
2. 훅이 관측하는 이벤트와 최종 변경 경계의 차이 확인
3. 직접 강제·부분 검사·사람 판단 항목 분류, 구체적 실패 사례 검토
4. 기존 구현을 재사용하는 최소 구조와 `HK-*` 수용 조건 제안

## 결론

프로젝트 전체에 공통 정책 검사 체계를 적용하는 방향 권장. 하나의 훅에 모든 규칙을 넣는 방식은 제외.

- 훅: 정해진 시점에 검사를 연결하는 호출 지점
- 정책 함수: 입력·현재 상태·권한을 검사하는 결정적 코드
- 최종 강제 지점: 파일 교체·지식 반환·Git 참조 변경·작업 상태 전환·원격 공개 직전
- 사람이 판단할 규칙: 목적 해석·설계 품질·설명 이해도·검토의 충분성

브랜치 사건은 규칙 파일 부재가 아닌 읽은 규칙의 잘못된 적용 사례. 문서 재전달만 추가할 경우 같은 실패의 재발 가능성 유지. 읽기·이해·준수·실제 결과를 구분하는 설계 필요.

## 이번 조사에서 확인한 구체적 공백

### 1. 계획 ID와 출시 검사기의 다른 문법

- 현재 등록 항목 69개 중 21개가 출시 검사기의 `PLAN_ID`와 불일치
- 예: 현재 `RF-B01`, 검사기가 받는 형태의 예 `RFB-001`
- 이 21개는 이전 리팩터링 계획 작성에서 도입한 이름. 제품 완료 뒤 출시 연결에 사용할 수 없는 현재 계약 불일치
- 근거: `scripts/check-test-release-gate.py`의 ID 정규식과 `PLAN.md`에 등록된 상세 계획의 읽기 전용 대조
- 수정 방향: 항목 ID의 단일 규약과 기존→새 ID 대응표, 모든 현재 참조의 함께 이관. 정규식을 무조건 넓혀 불명확한 ID를 수락하는 해결 제외
- 이 분석에서 실제 계획 ID나 출시 코드는 변경 없음

### 2. 현재 계획과 출시 검사기의 집계 대상 차이

- 문서 규칙: `PLAN.md`의 `Active fragments`에 등록된 문서만 현재 집계
- `checked_plan_ids()`: `docs/plans/active/*.md` 전체에서 체크된 ID 수집
- 현재 등록 범위 밖의 체크된 ID 187개가 수집되는 결과 확인
- 의미: 훅·진행률·출시 검사가 서로 다른 완료 집합을 참조할 가능성
- 수정 방향: 활성 문서·버전·항목·증거를 같은 파서에서 해석, 그 결과를 집계·종료·출시에 재사용
- 실제 출시 우회나 잘못된 게시의 성공을 시험한 결과는 아님. 추가 출시 조건의 존재와 구분

### 3. 보조 훅의 입력 주장이 실제 증거처럼 보이는 문제

- `update_integrity_guard()`는 `dry_run`, `backup_present`, `staging_validated`의 true 여부로 판정
- 이 함수 자체에는 백업 파일·준비된 내용·실제 갱신 기록을 확인하는 인자나 조회 없음
- `protect_hive_owned_state()`도 전달받은 작업 종류·경로를 판정. 임의 셸 내부의 모든 쓰기를 알아내는 기능 아님
- 수정 방향: 위험한 변경의 최종 승인에는 해당 갱신 처리 내부가 수집한 실제 상태 사용, 모델이나 호출자가 제공한 완료 주장만으로 허용 금지
- 이것은 보조 훅의 한계. 실제 `hive-update`의 백업·복구 검증 부재를 뜻하지 않는 구분

### 4. 호스트 연결과 실패 의미의 차이

- Hive 전용 입력·종료 `3`과 호스트의 입력·거부 결과는 서로 다른 계약
- 현재 보조 훅의 오류·자료 부재는 허용 종료, 새 필수 쓰기 검사의 실패 거부와 상이
- 소스·소비자 구분 없이 현재 훅을 전역 적용하면 잘못된 대상 검사나 필요 없는 작업 차단 가능
- 현재 일반 훅의 기능 범위는 제한적. 프롬프트 분류·자동 기억 저장·Skill 실행·작업 조율의 포괄적 이전은 기존 소유권과 충돌
- 수정 방향: 필요한 보호만 선택한 명시적 적용 범위, 호스트별 변환, 오류 시 동작의 분리

## 처음부터 설계할 경우의 최소 구조

### 정책 목록과 검사 코드

처음에는 규칙 목록을 Markdown으로 정리하고, 각 항목을 기존 검사 함수에 연결. 전용 규칙 언어·새 데이터베이스·상시 서버·모델 기반 검사기는 도입하지 않는 방향.

항목별 최소 정보:

- 규칙 ID·목적·소스/소비자/사용자 범위
- 적용 작업·현재 정본·검사 함수·최종 강제 지점
- 필요한 상태·정확한 권한·오류 처리·읽기 및 복구 경로
- 허용·거부 시험·호스트별 지원 범위·검증 자료

명령·설치 안내·현재 지원 표는 같은 목록에서 파생. 사람용 설명과 코드가 같은 문자열이어야 한다는 요구 대신 검사 의미와 사례의 일치 확인.

### 호출 흐름

1. 호스트 변환기가 공식 이벤트에서 작업 자료 추출
2. 검증된 대상과 해당 작업에 필요한 규칙 선택
3. 기존 검사 함수가 현재 상태·권한 확인
4. 호스트가 지원하는 거부·안내 결과로 변환
5. 실제 파일 변경·지식 반환·공개 직전에 해당 소유 코드가 다시 현재 상태 확인
6. 제한된 결과만 기록, 유효한 증거를 후속 상태 계산에 연결

훅 시점의 허용은 이후 모든 작업의 영구 허가가 아닌 범위. 검사 이후 파일·권한·정책이 바뀌면 변경 직전 재검증 필요. 고정된 대상 핸들·현재 지문·세대·허가의 기존 결합 재사용.

단일 판정 모양의 후보: `allow|deny|unsupported|error`와 규칙 ID·이유·정책 지문·확인한 증거. 공통 모양이 도메인별 권한·상태를 대신하지 않는 조건.

제품의 판정은 기존 Rust 소유 모듈에 유지. 소스 전용 Python 검사기를 소비자 배포물에 억지로 포함하지 않고, 필요한 공통 결과만 연결. 실제 두 경로에서 같은 책임이 확인된 경우에만 코드 추출.

### 오류 처리

| 작업 종류 | 검사 실패 시 동작 |
| --- | --- |
| 기밀 조회·보호 파일 변경·설치·공개 | 해당 작업 거부와 구체적 복구 안내 |
| 시작 시 규칙 안내·지침 로드 관측 | 경고와 제한 표시, 일반 대화 전체 차단 제외 |
| 상태 확인·취소·복구 | 해당 목적에 필요한 좁은 권한 검증, 망가진 일반 실행 검사에 종속 금지 |
| 지원하지 않는 도구 경로 | 미지원 명시, 다른 최종 강제 경계의 존재 여부 표시 |

호스트가 훅 오류를 허용으로 처리할 수 있는 경우, 훅 안에서 거부한다고 주장하는 것만으로 필수 변경 보호 증명 불가. 해당 쓰기 함수나 서버에서도 같은 권한 검사 필요.

### 비용과 개인정보

- 명령마다 전체 문서·전체 시험·전체 지식 색인 재검사 제외
- 자주 호출되는 훅은 해당 작업의 작은 상태만 확인, 무거운 검사는 저장·커밋·출시 등 명확한 단계에 배치
- 정책 내용 지문은 캐시 가능, 사용량·기밀 승인·쓰기 대상의 변하는 권한은 재사용 제한
- 판단 기록은 규칙 ID·자료 지문·결과·필요한 상태에 한정, 전체 대화·명령 원문·자격 증명 저장 제외
- 동일한 동작을 사용자 훅·프로젝트 훅·플러그인 훅이 중복 처리하지 않는 설치·철회 규약
- 외부 네트워크·모델 호출 없는 빠른 판정 우선, 호스트별 시간 예산은 기준 측정 후 확정

## 훅만으로 해결할 수 없는 사례

- 정상 이름의 셸 스크립트 내부에서 다른 프로그램이 파일을 덮어쓰는 동작
- 이미 열린 터미널에 나중에 전달된 입력, 훅이 적용되지 않는 도구나 외부 편집기
- 프로그램이 만든 거짓 시험 성공 자료, 잘못 정의한 완료 기준, 의미 없는 테스트
- 같은 OS 권한으로 정책 코드·Git 설정·보호 대상 자체를 함께 바꾸는 동작
- 외부 서비스에서 이미 전송된 메시지나 공개된 자료의 사후 발견

필요한 대응: 최종 변경 함수의 검사, 권한이 제한된 실행 환경, 원격 보호, 독립 검토. 더 강한 격리가 필요하면 호스트·운영체제 권한 구성을 별도 제품 결정으로 검토. 이번 분석에서 그러한 격리 환경을 설치하거나 확인한 결과는 없음.

## 세 호스트에 대한 적용 판단

- Codex: 실행 전 훅은 후보이나 일부 도구 경로와 기존 명령의 후속 입력이 제외 가능, 정의의 신뢰 승인 필요. [공식 문서](https://learn.chatgpt.com/docs/hooks)
- Claude Code: 실행 전 거부는 가능 후보, 지침 로드 관측은 비차단 이벤트. [공식 문서](https://code.claude.com/docs/en/hooks)
- Antigravity: 실행 전 `deny`와 모델 호출 전 주입은 후보, CLI·IDE·오류 처리의 실제 수용은 별도. [공식 문서](https://www.antigravity.google/docs/hooks)

상세 공식 계약과 설치본 조사: [이전 호스트 조사](host-policy-hooks-2026-09-18.md). 문서상 지원·설치된 기능·실제 거부 성공의 구분 유지. 세 제품 전체에 대한 실동작 완료 주장 없음.

## `0.11.0`에 적용할 순서 제안

1. `RF-S01`·`HK-001`: ID 문법·활성 항목·정책 목록·실제 강제 지점의 단일 규약
2. `RF-P01–P02`: 소유 파일·기밀 접근·갱신·공개의 기존 검증 경로와 누락 진입점 대조
3. `HK-002`: Codex 우선의 최소 호스트 변환, 이후 실제 계약이 확인된 다른 호스트 확대
4. `HK-003`: 직접 명령·도구 별칭·셸·MCP·자식 실행·취소·오류의 실제 범위 수용
5. `HK-004`: 지침만 제공한 기준선과 비교, 위반 성공·오탐·추가 시간·문맥 비용 측정
6. 위험도가 낮은 문체·계획 알림은 관측 모드에서 시작, 확인된 결정적 보호부터 차단 활성화

처음에는 브랜치·보호 파일·기밀 지식·갱신 및 공개 경계를 우선. 의미 판단이 큰 질문·Skill 선택·문장 품질은 보조 검사로 유지. 모든 기능을 한 번에 전역 훅으로 승격하는 작업 제외.

## 완료를 증명할 방법

- 규칙마다 허용·거부·모호한 입력·변경 도중 상태 교체·호스트 우회 자료 포함
- 같은 검사를 훅과 직접 CLI 경로에서 실행, 호스트를 거치지 않아도 보호되는 범위 확인
- 검사 실패·시간 초과·미신뢰·정책 갱신·훅 중복·중단 재개·하위 폴더에서의 적용 확인
- 보호된 변경의 실패 시 바이트 불변, 정상 고정 사례의 오탐 0건 목표
- 증거는 소스·정책·설치본·운영체제·호스트 버전·실행 경로별로 분리
- 실행한 사례만 분모에 포함, 미지원·미실행 경로를 성공률에서 숨기지 않는 보고
- 설명의 쉬움·목적 충족·검토 충분성은 별도 평가, 프로그램의 허용 결과로 대체 금지
