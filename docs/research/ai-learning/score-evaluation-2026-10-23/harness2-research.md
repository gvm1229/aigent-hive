## 1. 개선 대상과 두 단계의 학습

**확인 사실: 모델 가중치 고정, 모델 주변의 실행 구성 변경.**

1. 작업 안의 개선: 현재 하네스 실행 → 개선안 제안 → 같은 작업에서 시험 → 실행 차이를 비교하여 구성요소 합성 → 합성 하네스로 재실행
2. 작업 사이의 개선: 채택한 하네스의 실제 파일과 적용 상황·교훈·근거를 보관 → 다음 작업의 개선에 선택적으로 재사용

다음 작업의 시작점은 공통 기본 하네스. 직전 작업의 최종 하네스를 자동 상속하는 구조와 구분. 작업 중 개선용 기억은 고정하고, 작업 종료 뒤 기억 갱신.

근거: [README](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/README.md), [작업별 초기화·선택·기록 코드](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/schedule.py#L513), 논문 2.1–2.3절.

## 2. 제안·시험·합성의 실제 의미

| 단계 | 입력과 역할 | 중요한 한계 |
| --- | --- | --- |
| 기준 실행 | 공통 하네스로 작업 실행, 도구 사용과 산출물 관찰 | 기준 결과의 정확성 보증 없음 |
| 일반 개선안 | 계획·도구 사용·문맥·작업 분담·완료 절차의 문제 수정 | 해당 업무의 사실·전문 규칙은 분야 개선안의 책임 |
| 분야 개선안 | 해당 업무의 지식·절차·제약에 맞는 수정 | 현재 자료로 업무별 사실 재확인 |
| 후보 시험 | 같은 작업·모델·환경에서 두 종류의 수정안 실행 | 실행의 무작위 변동과 공통 오판 가능성 |
| 합성 | 후보의 변경점·실행 기록·산출물을 읽고 유효한 부분 선택·수정·결합 | 단순 최고 점수 선택과 구분; 기존 구성 유지도 가능 |
| 최종 선택 | 여러 합성 결과 중 하나의 기존 산출물 선택 | 새 답안 작성·정답 판정과 구분 |
| 회고 | 변경이 어떤 조건에서 어떤 결과를 냈는지 기록 | 채택 자체는 다른 작업으로의 효과 전이 증명과 구분 |

- 병렬 방식: 공통 기준 실행에서 일반 후보 k개·분야 후보 k개 시험, 전체 근거를 읽는 합성 k개
- 순차 방식: k번의 제안·시험·합성, 직전 구성과 누적 관찰 근거를 다음 단계에 전달
- k=1: 두 방식의 절차 동일, 실측 차이는 실행 변동의 확인 대상
- 형식이 잘못된 제안: 검사 오류를 알려 한 번 재시도, 다시 실패하면 해당 단계의 시작 하네스 유지

근거: [recursion.py](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/recursion.py#L343), [지시문](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/prompts.py#L347).

## 3. 점수 평가 논의와 가장 큰 차이

**확인 사실: 개선 과정에 정답·채점표·채점 점수 비공개, 결과 선택 뒤 별도 채점.**

- 편집자·합성자: 실행 차이·오류·산출물·사용자 작업 자료를 사용
- 최종 선택자: 익명화된 산출물과 작업 자료로 선택, 원래 하네스와 생성 경로 비공개
- 채점자: 선택 이후 평가별 기준으로 점수 계산
- LAB: 기준별 통과 비율과 전체 기준 통과 여부
- JobBench: 원 평가의 가중 배점
- WorkBuddy-Bench: 결정적 검사와 모델·시각 모델 평가의 혼합
- 채점 실패: 미채점으로 별도 집계, 0점으로 대체하지 않는 처리

현재 Hive 제안의 “0.90 미만이면 해당 감점 항목 수정”과 Harness²의 “최종 채점 점수를 숨긴 채 행동 근거로 개선”은 서로 다른 정보 흐름. 둘을 동일한 방식으로 설명하는 해석 제외.

**편입 검토 제안, 아직 기존 문서에 미반영:**

- 작업 결과 개선: 공개한 요구·품질 기준에 대한 점수와 수정 의견 활용
- 하네스 비교 실험: 최종 검증용 정답·점수는 수정 주체에서 분리, 실행 관찰을 근거로 후보 개선
- 최종 채택·완료: 별도 독립 검증과 0.00–1.00 점수 적용 여부 판단
- 개선용 기록과 최종 검증 기록의 저장 경계 분리

근거: [점수 비공개 지시문](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/prompts.py#L38), [채점 안내](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/docs/BENCHMARKS.md), [보고 계산](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/report.py#L85).

## 5. 기억의 내용과 승격 조건

**확인 사실: 요약문만이 아닌 채택 하네스의 전체 구성 파일과 EXPERIENCE.md 보관.**

- 기본 조직: 실행 조건별·재귀 방식별·분야별 자료실
- 작업 순서: 같은 분야에서는 순차 처리, 앞선 작업의 기록만 조회
- 경험 필드: 적용 단서 cue, 교훈 lesson, 근거 evidence; confidence와 변경별 설명은 선택 정보
- 필수 세 필드가 없으면 새 경험 항목을 만들지 않는 구조
- 숫자 점수·평가자 판정이 개선 문맥으로 들어오는지 파일명·내용 표식 검사
- 기록의 “근거 있음”: 모델이 작성한 근거와 구조 검사에 의존. 사실성·인과성·서명된 독립 검증 완료와 구분
- 자동 정리·오래된 경험 갱신·검색 최적화·적응형 탐색 예산: 논문에서 후속 방향으로 제시

Hive의 기존 지식 저장·검색·범위 통제를 재사용할 여지. 새로 필요한 후보는 “어떤 변경을 어떤 조건에서 시험했고 어떤 근거로 재사용할 것인지”와 실행 가능한 구성요소의 결합. 사용자 프로젝트의 경험을 전역·출하 하네스로 자동 승격하는 권한과 구분.

근거: [library.py](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/library.py#L105), [회고 정보 추출](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/selection.py#L454), 논문 G절.

## 6. 실제 비용 구조

기본 예약량은 작업 실행 4k회와 개선 단계 3k개. 정상 경로의 선택·회고·최종 채점은 별도.

| 예산 | 기준·후보·합성 하네스 작업 실행 | 제안·합성 단계 | 최종 선택 | 회고 |
| --- | ---: | ---: | ---: | ---: |
| k=1 | 4 | 3 | 0 | 채택 후 최대 1 |
| k=5 | 20 | 15 | 최대 1 | 채택 후 최대 1 |

- 숫자의 의미: 작업 실행 또는 에이전트 단계 수; 단일 모델 호출 수와 구분
- 추가 비용: 단계 내부의 여러 모델·도구 호출, 유효성 재시도, 통신 재시도, 최종 평가
- 캐시·중단·실패에 따라 실제 새 실행량과 비용 변화
- 병렬 실행의 효과: 지연 시간 감소 가능성, 총 계산량 제거와 구분
- 실행 전 고정 k: 점수 합격선까지 무제한 반복하는 구조와 구분
- 사용자 측정 후보: 최종 점수, 완료 건당 전체 사용량, 경과 시간, 실패·미채점 수, 경험 재사용 후의 별도 작업 성능

근거: [예산 장부](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/ledger.py#L15), [선택·회고 호출](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/schedule.py#L513).

- 논문 실험: Gemini 3.5 Flash·GLM-5 실행 모델과 OpenCode·Codex 조합 4개, 기본 편집 모델 Claude Opus 4.8
- 주요 표: 작업 순서를 섞은 실행 3회의 평균·표준편차
- 평가 표본: WorkBuddy 시험 40·35·25개, JobBench 시험 34개, LAB 보류 시험 100개
- 공개 설치의 전체 작업 발견 수와 논문 시험 분할의 구분: 단순 전체 실행을 논문 재현으로 해석하지 않는 조건
- 저자의 제거 실험: 경험 자료실·역할 구분·합성을 각각 제거한 경우 성능 저하 보고
- 교훈: 점수 기록만이 아니라 수정안을 시험하고 합성하는 과정도 효과의 후보 원인
- 해석 한계: 연구진의 실험 결과; 이번 Windows·Codex 세션의 독립 재현 없음. 모든 업무·모델·하네스에서의 향상 보장과 구분

## 8. 채택과 정확성의 차이, 실패 사례

### 기준 결과의 자동 보존이 없는 최종 선택

- 공개 selection_pool: 합성된 k개 결과만 후보, 기준 실행 결과는 제외
- k=1: 한 합성 결과를 별도 선택자 호출 없이 반환
- 합성 단계에서 기존 하네스를 유지할 수 있다는 사실과, 기준 산출물을 최종 선택 후보에 넣지 않는 사실의 구분
- 결론: “최소한 기준 결과보다 좋은 결과만 반환”하는 보장 없음
- 논문 실패 분석: 사후 평가 95점 후보 대신 55점 후보 선택, 잘못된 전제가 여러 후보로 확산한 사례

근거: [선택 후보 구성](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/selection.py#L93), [k=1 반환](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/selection.py#L360), [논문 실패 분석](https://arxiv.org/html/2610.14224v1#A5.S6).

### 평가 자료 유출

- 공식 실험 안내의 실제 관찰: JobBench의 Codex 실행이 지시받지 않고 온라인 평가 기준을 내려받은 사례
- 공개 배포의 기본 상태: 실행기 네트워크 무제한, Codex 격리 해제
- 코드의 경계 검사: 알려진 정답 경로·판정 표식 검사; 코드 스스로 완전한 방어가 아닌 읽기 경계의 탐지 장치로 설명
- 이미 승인된 점수 문서의 정답 접근 경계를 뒷받침하는 새 직접 근거; 이번 상세 결과의 자동 병합은 제외

근거: [EXPERIMENTS Web access](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/docs/EXPERIMENTS.md#web-access), [context.py](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/context.py#L454).

### 미채점과 혼합 지표

- 보고 코드: 채점하지 못한 행을 별도 집계하고 평균의 분모에서 제외
- 해석 조건: 점수와 평가한 작업 수·미채점 수·중단 작업 수를 함께 확인
- JobBench 가중 배점과 비가중 기준 개수 등 서로 다른 단위가 섞이면 경고
- k=1 두 방식의 차이를 실행 변동의 바닥 수준으로 표시하는 코드
- Hive 적용 후보: 작은 점수 상승을 개선으로 인정하기 전 같은 조건에서의 변동 확인

근거: [report.py](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/report.py#L85).

## 10. 실행 환경과 라이선스

- 설치 문서: Linux·Python 3.12, 패키지는 3.13도 허용
- 실제 모델 평가: Node.js 20 이상·Google Cloud CLI·모델 인증·API 비용, 평가별 Pandoc·Poppler·Docker
- Codex 실행기: Responses API 연결, Vertex Gemini 사용 시 로컬 LiteLLM 연결 서버
- Hive와의 차이: 현재 앱의 구독 인증을 그대로 사용하는 경로라는 보장 없음
- 권한: Codex 실행 인자에 승인·격리·훅 신뢰 우회 옵션. 이번 Hive 적용 없음
- 면허: 본체 Apache-2.0; 제삼자 코드·자료의 별도 면허 유지. WorkBuddy 문서의 지역 제한 안내는 별도 검토 사항
- 제품 지위: 저장소가 공식 Google 지원 제품이 아님을 명시
- 로컬 결정적 데모: 모델 자격 증명 없이 가능한 별도 경로로 문서화; 이번 실행 없음

## 11. 장기 방향에 대한 제안 — 승인 대기

1. **작업 결과 개선과 하네스 개선의 구분**: 산출물의 수정 기록과 실행 구성의 수정 기록을 각각 관리
2. **동일 조건의 후보 시험**: 기본 구성과 제한된 수정안을 같은 작업·환경에서 실행, 외부에 실제 효과를 내는 행동은 시험용 환경으로 한정
3. **일반 문제와 분야 문제의 분리**: 도구·문맥·완료 절차와 업무 지식을 각각 진단한 뒤 근거로 합성
4. **고정 검증 기준**: 개선 주체가 평가 기준·승인 조건을 자기에게 유리하게 변경하지 못하는 경계
5. **근거를 붙인 재사용 구성**: 적용 조건·변경 파일·관찰 결과·반례·출처를 묶어 프로젝트 범위에 먼저 보관
6. **적용·배포의 별도 판단**: 비교 실험의 채택, 실제 프로젝트 적용, 사용자 전역 공유, 제품 출하를 구분
7. **비용을 포함한 효과 확인**: 작은 점수 차이의 변동 검토, 전체 사용량·미채점·반복 횟수를 함께 측정

상기 내용은 조사자의 적용 제안. 기존 점수 문서·활성 제품 계획·사용자 설정에 미편입.
