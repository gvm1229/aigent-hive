# 예시 협업 프로젝트의 Hive 갱신 계획

> 상태: 6단계 완료, 공개·설치·실제 사용·예시 갱신·Git 통합 검증 완료
> 대상: 사용자가 지정하고 경로를 확인한 예시 프런트엔드 프로젝트
> 사용할 버전: `0.11.0-test.6`, 소스 `797e5ab579f20268eeff489d1cc7cdbd023a188b`

## 목적과 선행 검증

- 목적: Hive 미설치 협업자의 일반 작업 허용과 기존 사용자 규칙·작업 파일 보존
- [제품 검증 기록](project-directives-collaboration-0.11.0.md): 생성기·설치 상태별 반응·기존 설치 갱신·복구·보존 확인
- [공개 시험판](https://github.com/gvm1229/aigent-hive/releases/tag/v0.11.0-test.2), [세 운영체제 공개 수용](https://github.com/gvm1229/aigent-hive/actions/runs/35794230854) 완료 후 작성
- 후속 선행 조건: [갱신 스킬 검증](project-refresh-exposure-0.11.0.md)의 test.6 공개·설치·자연어 갱신 완료. 과거 기준본 인증·지침 경로 예약·Windows 줄바꿈 표시 병합 수정 포함
- 현재 단계: 공식 갱신·보존 검사·Hive 전용 커밋·develop PR 통합 완료. 원래 작업 폴더의 최종 검사 재통과
- 정확한 사용자 경로·작업 내용은 공개 소스에 복제하지 않고 실제 적용 시 다시 확인

- 용어: 브랜치는 변경을 따로 쌓는 작업 공간, 커밋은 변경 묶음의 기록, PR은 합치기 전 검토 요청, Git 인덱스는 다음 커밋에 넣을 변경 목록

## 읽기 전용 확인 결과

- 기존 Hive 버전 `0.10.3`, 인증 기준본 목록 29개. `develop`에도 Hive 기준본 존재 확인
- 사용자 작성 `AGENTS.md` 영역, Next.js 표시 블록, Hive 표시 블록의 공존
- `.agents/directives/05-behavior.md`부터 `10-security.md`와 프로젝트 `ship` 스킬은 사용자 소유. 확인한 범위에서 별도 Hive CLI 강제 명령 부재
- 개인 작업 브랜치에 진행 중인 앱 변경 존재. 현재 작업 상태를 갱신 전 기준으로 고정하거나 모두 커밋하는 조치 제외
- 프로젝트 Git 규칙: 작업 브랜치 → `develop` PR, `main` 직접 변경 금지
- 지침 변경의 프로젝트 검사: 링크·형식·충돌·원본 보존, 폴더 변경 시 `pnpm check:structure`
- `pnpm typecheck`·`pnpm test`·`pnpm build`·`pnpm test:e2e`는 해당 앱 변경이 있을 때 추가 적용. 이번 지침 갱신만으로 전체 앱 시험을 필수화하는 조치 제외

## 승인된 6단계 실행 순서

### 1. 작업 상태와 적용 위치 확정

- 대상 루트·설치 버전·현재 브랜치·Git 인덱스·미커밋 변경·진행 중인 다른 작업 재확인
- 기존 앱 작업의 stash·reset·clean·무관한 커밋·임의 브랜치 전환 금지
- 현재 확인: Hive 관리 파일과 Git 인덱스에 미커밋 변경 없음. 원래 작업 폴더에 공식 적용해 정확한 백업 생성, 관련 커밋만 별도 작업 폴더로 옮겨 develop PR 구성
- 계속 진행 중인 사용자 작업과 분리할 필요가 있으면, 승인된 `develop` 기반 작업 브랜치와 별도 작업 폴더에서 준비. 브랜치 예: `fix/hive-optional-collaboration`
- 별도 작업 폴더의 목적: 실제 작업 폴더 보존. 원래 프로젝트의 지식 연결이나 사용자 전역 설정을 임의로 복제·재등록하는 용도로 사용 금지
- Hive 관련 경로에 다른 작업의 쓰기가 겹치면 해당 적용만 대기. 무관한 앱 작업 전체의 중단 요구 제외

### 2. 검증된 실행 파일과 기준 자료 확보

- `0.11.0-test.6` 공개 실행 파일의 버전·공개 출처·내용 지문 확인. 지문은 파일 내용이 달라졌는지 확인하는 값
- 검증된 제품 지문: `sha256:1d84f8c47676e73e30da0f7ef25b09c85de55da665b542cf348b967621118a53`
- 제품 지문은 소스 제품 파일 묶음의 값이며 실행 파일 자체의 지문과 구분. 실행 파일은 해당 공개 배포 파일의 체크섬·서명 근거로 확인
- 전역 설치는 승인된 PRF-002에서 검증. 6단계에서는 그 실행 파일을 명시적으로 선택하고 설치된 `project-refresh` 스킬 사용. 사용자 설정 호환성 오류의 우회 금지
- `0.10.3` 기준본 인증과 현재 Hive 소유 목록 확인. 누락·변조·지원하지 않는 형식이면 적용 중단
- Hive 관리 파일과 공유 파일의 Hive 표시 블록 전후 내용·지문, 사용자 소유 파일의 지문 확보. 자격 증명·전체 사용자 대화·앱 비공개 자료의 별도 수집 제외

### 3. 미리보기와 복구 준비

아래 명령의 `<검증한 Hive 실행 파일>`과 `<적용 작업 폴더>`는 앞 단계에서 확정한 값으로 치환. PRF-002 완료 전 예시 프로젝트 실행 금지.

```text
<검증한 Hive 실행 파일> project upgrade --target <적용 작업 폴더> --scan --output json
<검증한 Hive 실행 파일> project upgrade --target <적용 작업 폴더> --dry-run --output json
```

- `0.10.3 → 0.11.0` 누적 변경 전체의 실제 차이 검토. 이번 협업 지침 몇 줄만 수동 교체해 소유권·기준본 기록과 불일치시키는 조치 금지
- 예상 검토 영역: Hive 표시 블록, 관리 지침, 선택된 스킬과 그 지문 목록, 버전·소유권 관련 생성 설정
- `.agents/directives/05-*`부터 `10-*`, 프로젝트 `ship`, Next.js 표시 블록, 앱 소스·계약·사용자 설정의 기존 바이트 보존 확인
- 미리보기의 기준·현재·새 파일·최종 결과 지문과 충돌 판정 확인. 비충돌 사용자 메모 보존, 인증된 Hive 소유 절의 직접적인 안전·소유권 충돌만 제품 규칙에 따라 교체
- 적용 직전 지문 재확인과 복구용 백업 준비. 미리보기 뒤 관련 파일이 바뀌면 새 미리보기부터 재검토
- 백업 보관은 최대 7일 원칙과 별도 정리 절차 적용. 갱신에 지식 삭제나 일괄 정리를 결합하지 않는 경계

### 4. 적용과 결과 검사

```text
<검증한 Hive 실행 파일> project upgrade --target <적용 작업 폴더> --apply --output json
<검증한 Hive 실행 파일> project upgrade --target <적용 작업 폴더> --validate --output json
```

- 적용 결과와 변경 경로 확인, 새 기준본·스킬 지문 일치 및 공유 파일의 Hive 밖 바이트 대조
- 미설치·미초기화 협업자의 일반 작업 가능 여부, 설치된 Hive의 오류·사용량 중단 후 일반 모드 우회 금지 확인
- 다른 도구 설정 보존과 설치 요구·자동 도구 전환 부재 확인. 전역 Hive 제거로 미설치 환경을 만드는 시험 금지
- 필요하면 별도 합성 사용자 환경에서 위 동작 재확인. 실제 계정 사용량·다른 사용자 지식·전역 설정은 시험용으로 변경 금지
- 링크·형식·보존 검사와 필요한 `pnpm check:structure` 실행. 보호·권한·호환성 오류를 단순 미설치로 바꿔 진행하는 조치 금지

### 5. Git 반영과 실제 작업 폴더 확인

- 프로젝트 `ship` 절차에 따라 Hive 관련 변경만 목적별 커밋·`develop` PR로 반영
- 별도 작업 폴더의 PR 완료만으로 원래 예시 폴더 수정 완료 판정 금지
- 원래 개인 작업 브랜치에는 승인된 Hive 관련 커밋만 반영. 관련 경로 충돌이나 기존 인덱스 변경이 있으면 사용자 작업을 보존하고 그 단계만 대기
- 원래 예시 폴더에서도 새 버전·지침·소유권 검사를 재확인. 기존 앱 변경의 소실·무관한 파일 변경 0건 확인 후 실제 수정 완료 판정
- 별도 작업 폴더는 필요한 커밋·검증 기록 보존 후 정리. 안정판 통합·운영 배포는 별도 권한 범위

## 실패와 되돌리기

- 기준본·미리보기·승인 조건 불일치: 적용 전 중단, 현재 파일 유지
- 실행 중 일부 적용 실패: 제품의 자동 복구 결과와 백업 확인. 남은 작업 기록이 있을 때만 `project upgrade --recover` 사용
- `--recover`는 남은 작업 기록을 정합화하는 명령. 반환 결과는 `rolled-back` 또는 `forward-complete`일 수 있으므로 항상 이전 버전 복원으로 해석하는 조치 금지
- 성공한 적용은 작업 기록이 이미 제거될 수 있으므로 `--recover`를 일반 되돌리기 명령으로 사용 금지
- 성공 후 되돌리기가 필요하면 Hive 관련 커밋과 사전 백업만 대상으로 별도 검토. 이후 사용자 수정과 다른 지문 발견 시 덮어쓰기 중단
