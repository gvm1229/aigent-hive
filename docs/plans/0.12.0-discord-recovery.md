- 원인: 출시 때 현재 Codex가 `send_subscriber_update=false` 선택, 실제 전송 단계 제외. 게시·전송 오류가 아니라 전송 승인의 과도한 분리
- 현재 승인: 2026-10-06 사용자 명시 요청으로 누락한 Discord 공지 전송·복구. 승인한829자 안내문·배너 그대로 사용
- 추가 사용자 규칙: Discord 안내문 승인이 안정판 게시의 필수 선행조건. 승인 없는 게시 금지, 정식출시에서 공지전송을 제외하는 경로도 거부
- 공개 상태: 정식v0.12.0·main소스a257b4157048b07b40c53ce0f2d50542267772f5·게시37396583273 성공, 해당전송skipped
- 변경 범위: 공지 전용CI와 계약시험·유지관리 기록. 제품·패키지·정식태그·사용자설치·안내문 변경·재게시 제외

## 구현과 실행

1. `.github/workflows/release-discord-notification.yml`: main의 명시적workflow_dispatch만 허용, product_version과 publication_run_id 검증. 보호release-publication 환경의 기존 비밀을 사용하며 값을 출력·내보내지 않는 방식
2. 전송 전 GitHub정식출시·정확한게시SHA·성공한게시·기존전송skipped 확인. 해당버전의 전송성공 artifact가 있으면 중복거부, 버전별 concurrency로 동시전송 직렬화
3. 검증한 정식태그로 checkout. 기존 `publish-stable-discord-update.py`의 승인문구·외부지문 검증·배너먼저·안내문다음 전송 재사용. 새 모델·공급자API 호출 없음
4. 성공 뒤 webhook값·대화 원문 없는 영수증 artifact 저장: 버전·게시ID·출시SHA·문구/배너지문·글자수·두요청성공. 실제 수신자열람 증명과 구분
5. `tests/conformance/release/test_stable_release_discord_notification.py`: main/정식태그/성공게시/중복거부·전송검증 순서·게시명령부재 계약 확인. 기존21개이상 실제로컬HTTP 시험 유지
   - 기존 게시의 stable 분기에서 `send_subscriber_update=true` 필수, 생략·false는 게시전 거부. 기존 안정판 문구·외부 승인 지문의 사전검증은 전송선택과 무관한 필수조건으로 유지. 실제 shell에서 거부·허용과 미승인본문 검증의 게시앞 순서 확인
6. 목적별ship·develop push, develop → main 보호PR·필수검사·일반병합. 승인한0.12.0 공지복구범위의 source CI만, 제품 바이트 불변 확인
7. 공지전용workflow에서0.12.0·게시37396583273로 정확히1회 실행. 서버가두요청을수락하고 영수증이생긴 뒤 계획·현재상태·지식에 실제근거 기록

## 실패 처리

- 기존게시workflow 재실행·비밀값의 로컬복호화·정식릴리스삭제·재게시 금지

- 이 계획 완료는 공지의 서버수락 증명. 구독자열람·설치와 기존미완료9개호스트수용 완료 주장 제외
