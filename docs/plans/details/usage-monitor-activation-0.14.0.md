# 0.14.0 감시 활성화의 결합과 재개

G140-002의 하위 구현 순서. 별도 완료 집계 없음. 구현·검증·번호 공개 시험 승인 범위, 정식 게시·실제 사용자 설치·운영 감시 변경은 범위 밖.

## 현재 근거와 결정

- `usage_monitor.rs::enable`: 미리보기 지문 확인 후 실행 파일 준비·예약 등록·상태 초기화·구성 저장·시작. 현재 단계 사이의 중단을 재개할 처리 기록 부재
- `upgrade.rs::upgrade_with_choice`: 소유 검증·정확한 예약 교체·상태 보존·준비 확인 재사용 가능. 새 설치의 구성 부재와 새 동의는 별도 처리 필요
- `resume_after_setup`: 이미 저장된 새 구성에서 `complete` 기록만 허용. 준비 확인 도중 중단된 기존 감시 갱신의 재개도 검증 대상
- `75ad6ff7`: 구성 부재·같은 비활성 값에서도 해제 선택마다 새 `selection_id` 기록. 이후 해제 선택의 감지 자료이며 동의 증명이나 실행 권한과 구분
- 실행 전 기록과 관측 가능한 실제 상태로 재개. 확인되지 않은 외부 명령 결과를 성공으로 추정하거나 무조건 반복하는 방식 제외

## 1. 미리보기와 입력 결합

- 변경: `usage_monitor.rs::preview`, 새 `usage_monitor/activation.rs`의 결합 자료. 기존 `SavedMonitorChoice`와 정확한 사용자 폴더 식별자 재사용
- 기존 미리보기에 사용자 폴더의 실물 지문·현재 감시 구성 지문·최근 해제 기록 지문 추가. 파일·센서·예약 변경 없는 조회
- `preview_digest`는 해당 자료와 실행 파일·고정 어댑터·예약 작업·대상 범위를 함께 포함. 기존 JSON 필드 유지, 변경 뒤에는 새 미리보기 필요
- 검사: 같은 입력의 안정된 지문, 폴더 교체·해제 재선택·구성 변경의 다른 지문, 새 폴더 무쓰기. 다른 OS의 미지원 상태를 지원으로 표시하지 않는 조건

## 2. 활성화 처리 기록과 재개

- 변경: 새 `usage_monitor/activation.rs`와 필요한 기록 보조 모듈, `usage_monitor.rs::enable`, `upgrade.rs`의 준비 확인·재개 경로
- 기록: 처리 ID·사용자 폴더 결합·승인한 미리보기·원래 구성 지문·해제 기록 지문·목표 구성·현재 단계·쓰기 전후 지문·마지막 결과
- 단계: 준비→실행 파일 준비→기존 감시 정지 확인→상태 준비→구성 저장→예약 등록→시작→실제 준비 확인. 모든 변경 전에 해당 의도 저장
- 기존 상태 초기화는 새 활성화에서 한 번만 수행. 재시도로 조회 실패의 60초 구간이나 과거 사건을 초기화하지 않는 조건
- 파일 중간 교체는 `user_install`의 경로가 정해진 쓰기 보관·복구 도구 재사용. `run.rs::publish_runtime`의 임의 보관 파일만으로 새 처리의 복구를 대신하지 않는 경계
- 예약은 정확한 Hive 소유 이름·동작만 처리. 현재 구성과 기록으로 확인된 실제 결과를 재사용, 다른 사용자 선택·외부 변경은 보존 후 미완료 표시
- 더 늦은 해제 기록의 지문 변경은 이전 활성화 재실행 금지. 구성 부재 또는 같은 비활성 값도 해제 취소 신호로 구분
- 기한·부모 종료·외부 명령 결과 불명은 미완료와 재개 위치 반환. 외부 명령 시간은 현재 설정 작업의 잔여 기한 이내
- 검사: 모든 단계 전후 중단, 같은 처리 재개, 실제 결과 유실, 후속 해제, 외부 구성 변경, 준비 확인 실패. 모의 운영체제 호출과 실제 사용자 감시를 구분한 기록

## 3. 공통 설정 입력 연결

- M02 자료: 진행 기록의 `monitor_start`에 native 미리보기 지문·선택값 지문·입력 경로 저장. 선택값 지문은 출처/시각 메타데이터를 제외한 정규화 설정 전체, 파일의 `--monitor-confirm`은 두 지문의 결합값. 출처 기록을 실행 권한으로 사용하는 처리 제외
- `setup_engine/monitor_start.rs`에서 수집·파일 결합·완료 확인 통합. 터미널은 새 선택 또는 사용량 설정 재검토에서만 질문, 무관한 변경과 비대화형 유지의 자동 재활성 금지. 아니요는 midway 선택 비활성, EOF는 보류
- 최종 설정/하네스 검증 뒤 기존 M01 활성화 호출·검증 성공 후만 완료 기록. 입력 변경·다른 승인 지문 거부. 불완전 활성화의 새 검토/취소는 별도 복구 검사, 막힌 기록의 임의 삭제 제외

- 변경: `progress_store.rs`, `setup_engine`의 터미널·파일·작업자·재개 경로, `harness/setup/questions.yml`
- 새 활성화 또는 재활성화는 별도 기본 거부 질문에서 정확한 범위와 예약 동작 표시. 전체 설정의 최종 확인도 유지
- 명시적인 아니요는 상시 감시 선택을 비활성으로 정리한 뒤 미리보기 진행. 해당 질문의 출처 기록, EOF·취소는 답안 보관 후 보류
- 기존 활성 감시 유지·관련 없는 설정 변경·비대화형 소프트웨어 갱신에서 새 동의 추정 금지. 실제 비활성 선택의 자동 재활성 금지
- 파일·AI 입력은 `--dry-run`의 결합 자료와 별도 `--monitor-confirm <digest>` 사용. `--apply`·갱신의 `--confirm`만으로 보충 금지
- 지원하지 않는 환경에서 신규 활성화 적용 거부. 기존 선택 보존과 미지원 이유 표시, Windows 제어 호출 없음
- 처리 완료는 실제 적용·검증 뒤만 기록. 활성화 취소·충돌은 미완료 자료를 보존한 상태로 CLI의 명시적인 재검토 경로 제공

## 4. 검증과 합격 범위

- `python scripts/dev-check.py rust -- test -p hive-cli usage --locked`와 변경한 설정 회귀, 관련 정적 검사
- Windows 시험은 별도 사용자 폴더·가짜 앱·시험 예약에 한정. 현재 사용자의 Codex 대화를 제어하는 실제 감시 활성화 금지
- 실행 중인 실제 앱 제어가 필요한 수용은 개인 설치와 분리한 운영체제 환경에서 수행. 미실행을 모의 성공으로 대체하지 않는 기록
- 같은 버전에서 답변·동의·적용·재개를 완료하고 최신 해제 선택을 보존한 증거 필요. 마지막에 기존 해제·설정 조회·첫 갱신의 기한 회귀 확인
- 단계별 검증·`ship` 커밋 후 다음 단계 진행. 이 하위 계획의 저장이나 부분 통과를 전체 G140-002 완료로 처리하지 않는 조건

## 격리 Windows의 남은 실제 수용

- G140-002: 기존 활성화 기록과 공통 설정 연결 구현 보존. GitHub-hosted Windows에서 실제 예약·실제 감시 실행 파일의 앱 대기 상태부터 검증. Codex 플러그인 명령만 고정 대역, 개인 앱·설치·모델 호출 제외
- 최소 입력: 공개 질문 목록의 기본값에 보호/감시 선택 명시→파일 미리보기→별도 동의 없는 적용 거부→정확한 동의 적용→실제 실행/관측 상태 구분→보호 해제와 종료→새 동의 재활성·자료 보존. 운영체제 가용성1회 확인, 실패 시 정확한 단계와 결과 보존 후 확인된 원인만 수정
- 변경 경로: 기존 격리 시험 폴더의 Windows 실행기와 CI 연결. 제품 변경은 실제 실패 뒤 최소 범위, 기존 시간·소유·동의 조건 유지. 앱 부재의 대기 상태는 실제 Codex 관측·중단 증명에서 제외
