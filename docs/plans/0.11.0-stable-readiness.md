- 범위: 기존 DCR-006·RFR-001의 검증과 완료 판정. 새 제품 목표나 중복 완료 항목 추가 제외
- 승인: 차단 요인 없는 출시 준비까지 지속. develop 통합·번호 공개 시험 포함, main 통합·안정판 태그·게시·설치는 제외
- 실행 방식: 소스 계획 사용. 연결된 초기화·검증 영수증이 없는 Hive 실행의 활성 주장 제외
- 보존: 다른 작업의 미추적 UX 보고서, 과거 기준본, 사용자 설정. 실제 모델 시험의 한계·실패 기록 유지
- 근거: [test.9 수용 기록](../research/0.11.0-test9-qualification.md)

## 단계와 판정

1. **수정 검토·커밋** — `configure.rs`의 이전 정본 위치 허용과 `test_directive_context.py` 회귀를 독립 검토. 제품 수정, 시험 근거·지식, 출시 의도를 별도 커밋. 관련 Windows 검사 결과와 외부 설정 바이트 보존 확인 후 진행
2. **전체 검증** — `python scripts/dev-check.py pre-push` 실행. 전체 Rust·Python·형식·Clippy 및 소스 문서 검사 결과를 실행 기록에 결합. 실패는 원인별 최대 2회 수정·재시험, 동일 실패 반복 시 독립 작업 유지와 원인 조사; 검사 삭제·약화 금지
3. **다음 시험판 준비** — 공개 버전·GitHub 태그를 조회해 미사용 `0.11.0-test.9` 확인. 현재 제품 지문과 완료 구현 ID를 `docs/test-release-intent.json`에 결합, 양언어 시험판 안내 갱신. 설명은 사용자가 체감할 변화와 실제 증명 범위로 제한
4. **원격 후보·게시** — develop 푸시 뒤 정확한 커밋의 필수 CI와 Release candidate 확인. 성공한 후보 실행 ID로 test 채널만 게시. npm 버전·test 태그·GitHub 시험판을 독립 조회하고 latest=0.10.3 유지 확인
5. **공개 패키지 수용** — 같은 패키지로 Windows·macOS·Linux의 Public test acceptance 실행. 이전·보존·복구·훅 재등록 검사를 실제 공개 실행 파일에 적용. 후보 성공을 공개 수용으로 대체하지 않는 경계
6. **최종 준비 판정** — 실제 모델 근거·비용 측정의 한계와 기존 승인된 제외 범위를 재검토. 새 수정의 공개 수용 성공 뒤 DCR-006·RFR-001 근거 갱신, 계획 0건 미완료와 지식·출시 검사 확인. 준비 완료 자료와 정식 출시의 정확한 후속 행동을 제시

## 증거·중지·복구

- 독립 검토자: 읽기 전용 코드·수용 근거 검토. 실행 검증자: 기존 자동 검사·공개 레지스트리·운영체제별 수용
- 후보·게시·수용의 실행 ID, 소스 커밋, 패키지 버전·지문을 함께 기록. 게시 실패 시 기존 공식 복구 절차와 같은 바이트 여부 확인; 번호 재사용으로 수정 배포 금지
- 계획의 성능 목표를 통과로 꾸미지 않는 경계. 간단한 문구 비교와 실제 훅 동작·장기 품질은 별도 증거
- GitHub 환경 승인·사용량 보호·사용자 수동 조작이 필요하면 정확한 지점에서 중지. 독립적인 안전 작업은 먼저 완료
- 원격 실패 로그는 필요한 오류 구간만 조회. 원문 대화·숨은 지침·자격 증명 저장 제외

## 남은 실제 호스트 수용

- 기존 6턴 계측과 315,505토큰 결과·초과 기록 유지. 아래는 독립 검토가 지적한 미검증 조건의 추가 수용이며 이전 실행의 예산 초기화가 아닌 별도 범위
- 위치: `tests/work/readiness-host-acceptance/`, 제어 도구: `.agents/work/directive-context-approval/readiness_acceptance.py`. 현재 앱 동봉 Codex의 공식 연결·기본 모델 사용, 제공자 API 호출 제외
- 먼저 기본 파일 도구 지원 확인. 절대 합성 경로·현재 작업과 같은 권한 프로필에서 파일 바이트 검증. 실패 도구를 셸로 우회하지 않는 기준
- 고정 조건: 복원 없음·전체 문구·선택 구절 세 방식. 보호 검사·모델·자료·요청은 동일하게 유지. 시험용 복원 제어기는 승인한 합성 원문과 세 방식만 허용, 매 방식 전 정확한 훅 신뢰 확인
- 공통 과제: 큰 합성 자료 읽기 후 실제 자동 압축 → 정상 파일에 한 줄 추가 → 기존 사용자 내용 보존 → 합성 보호 파일 수정 1회 거부 → 한국어 완료 보고. 결과는 실제 파일·호스트 사건·완료 항목별로 채점, 안내 암송 제외
- 선택 조건의 같은 대화 재개 3회와 실제 하위 작업 3개 확인. 공식 재개·SubagentStart 사건과 별도 합성 결과 파일을 연결. 미지원이면 흉내 내지 않고 해당 기준 보류
- 사용량: 같은 요청의 첫 입력 토큰에서 복원 없는 기준 비용을 빼서 전체/선택의 새 안내 토큰 계산. 선택 비용이 전체의 절반 이하인지 확인, 실제 입력·출력·캐시·압축 비용의 한계 별도 기록
- 준비 후 공개 test.9 실행 파일을 고정해 검사. 새 훅 정의의 호스트 신뢰가 필요하면 다른 자동 준비를 마친 뒤 정확한 수동 조작 안내
- 추가 수용 예산: 기본 도구 확인 최대 2턴, 본 수용 최대 12개 호스트 턴·하위 작업 3개·보고 입력 1,000,000토큰. 각 턴 최대 180초. 다음 요청 전 잔여 예산 확인, 부족하거나 같은 실패 2회 반복 시 해당 노드 중지. 원문·추론 저장 없이 사건 종류·횟수·파일 지문·사용량만 보존
- 모든 조건 종료 뒤 원래 설정 복구, 사용자 신뢰 기록은 변경하지 않는 경계

- 최초 기본 조건: 실제 입력 23,518→33,498토큰으로 40,000 기준 미도달, 압축 0회로 실패 보존. 세 조건 모두 30,000으로 맞춰 1회 재시험. 초기 도구 확인과 실패 시도의 209,529 입력 토큰을 같은 예산에 계속 포함, 초기화 없음
